==================================================
WHAT TO AUDIT AND IMPROVE
==================================================

A. RESULT LANGUAGE HARDENING
Audit every place the app describes outcomes.

Requirements:
- Replace any overly reassuring or overly absolute wording
- Prefer:
  - “No obvious issue detected in this capture”
  - “Review recommended”
  - “Capture quality insufficient”
  - “Visible concern flagged”
- Avoid:
  - “safe”
  - “verified”
  - “authentic”
  - “approved”
  - “guaranteed”
  - “clean”
- Make sure “Pass” never implies safety or identity confirmation
- Make sure low-confidence results visibly state uncertainty
- Make sure poor capture quality cannot produce falsely reassuring language

B. RESULT LOGIC REVIEW
Audit the triage logic and confidence logic.

Requirements:
- Poor capture quality must strongly reduce confidence
- Poor capture quality should bias toward REVIEW, not PASS
- If the app cannot assess something reliably, it must explicitly say “unable to assess”
- If OCR is unreadable, say that directly
- If fill level cannot be estimated, say that directly
- If glare interferes, say that directly
- Ensure overall result logic is internally consistent across all categories

C. OCR UX HARDENING
OCR is real but imperfect and may load slowly.

Requirements:
- Add clear loading/progress state when OCR engine is loading
- Add user-facing copy explaining first-run OCR may take longer
- If OCR fails, handle gracefully without crashing or hanging
- If OCR output is low quality, present it as low confidence / partial match / unreadable
- Make OCR feel assistive, not authoritative

D. CAMERA / CAPTURE UX HARDENING
Requirements:
- Make capture instructions extremely clear
- Ensure every capture step explains what the user should photograph
- Ensure retake flow is clean and obvious
- Ensure permission denial or failed capture has a working fallback path
- Ensure file upload fallback is easy to use
- Ensure user always knows what step comes next

E. EDGE-CASE HANDLING
Audit and improve behavior for:
- no image selected
- corrupted image
- too dark image
- too bright image
- blurry image
- image too small
- label skipped
- label unreadable
- history empty
- history corrupted in localStorage
- resumed session partial data
- direct route refresh on any page
- analysis failure in one category
- analysis failure in multiple categories

Requirements:
- no crashes
- no blank screens
- no dead buttons
- no trapped state
- graceful recovery whenever possible

F. HISTORY / STORAGE HARDENING
Requirements:
- verify save works every time
- verify detail view loads correctly
- verify delete works
- verify clear-all works with confirmation
- verify corrupted or malformed localStorage does not break app
- add guard rails / fallback parsing if needed
- keep data model stable and consistent

G. MOBILE FINISH PASS
This app must feel good on a real phone.

Requirements:
- review spacing at mobile widths
- ensure touch targets are large enough
- ensure sticky CTAs are not blocking content
- ensure long result cards are readable
- ensure collapse/expand interactions feel obvious
- ensure typography hierarchy is clear
- ensure scan progress is obvious on mobile
- ensure footer disclaimers do not overwhelm the UI

H. COPY POLISH
Audit the entire app copy.

Requirements:
- remove repetition
- reduce unnecessary legal-sounding verbosity while keeping caution
- keep tone serious, practical, and trustworthy
- make instructions short and clear
- make the home screen feel purposeful
- make the results screen feel calm and useful, not alarming or gimmicky

I. SMALL UX IMPROVEMENTS ONLY
Allowed:
- better loading states
- better empty states
- better disabled states
- clearer button labels
- better inline help
- clearer retake flow
- better result emphasis hierarchy
- smoother transitions
- better error banners/messages

Not allowed:
- full redesign
- new product modules
- account system
- backend sync
- exports
- community
- ecommerce
- AI chat
- large architecture rewrite unless required to fix a serious issue

J. CODE QUALITY HARDENING

- reduce obvious duplication where safe
- improve naming if confusing
- ensure no console errors
- ensure TypeScript clean
- ensure no dead code from abandoned attempts
- ensure components and helpers remain understandable
- add concise comments only where logic is genuinely non-obvious
